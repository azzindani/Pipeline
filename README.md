# Pipeline

> **Local-first CI/CD + MCP for any coding agent.**

Pipeline removes infrastructure burden from coding agents. Any agent — Claude Code, Codex, opencode, Kilo, Ollama, LM Studio, custom — locks into a project, gets full context handover, and drives the entire lifecycle (idea → PRD → scaffold → code → test → deploy → maintain) through a stable 19-tool MCP surface. Local CI is the source of truth · GitHub Actions is confirmation · Docker is the substrate · standards are enforced automatically · memory accumulates per project.

> **Status:** 19 / 19 tools functional · 172 / 172 actions wired · hand-rolled JSON-RPC + rmcp 1.6 transports · POC complete · most of MVP shipped. See [`PLAN.md`](PLAN.md) for the full roadmap and [`CLAUDE.md`](CLAUDE.md) for the agent-facing reference.

---

## Why Pipeline

Coding agents are fast at writing · slow at validating. Pipeline inverts the loop:

```
Agent generates code → Pipeline validates locally (fast stage · seconds)
                    → Agent fixes from memory (suggest_fix learns from past failures)
                    → green → push → confirm → deploy
```

Everything meaningful happens before the push. GitHub Actions becomes a trust signal, not the primary gate. Local models (Ollama · LM Studio) become viable for real software delivery because Pipeline hides infrastructure complexity behind clean MCP tools — the agent calls `pipeline_run.stage(fast)`, not `cargo fmt && cargo clippy && cargo test`.

## Install

### From source (recommended for now)

```bash
git clone https://github.com/azzindani/Pipeline.git
cd Pipeline
cargo build --release
# Binary lands at target/release/pipeline
```

Add to PATH:

```bash
sudo install -m 0755 target/release/pipeline /usr/local/bin/pipeline
# or symlink during development:
ln -sf "$(pwd)/target/release/pipeline" ~/.local/bin/pipeline
```

### Requirements

| Component | Why · how to install |
|---|---|
| Rust 1.85+ | `curl https://sh.rustup.rs -sSf \| sh` |
| Docker 24+ | container · integration · e2e · security stages run containerized tools |
| Git 2.40+ | session locking · `pipeline_run.commit/push` · `pipeline_repo.register` |
| `cargo-llvm-cov` (optional) | needed only for `pipeline_test.coverage` · `cargo install cargo-llvm-cov` |
| `cargo-audit` (optional) | needed only for `pipeline_security.dep_audit(rust)` · `cargo install cargo-audit` |

### Docker (planned · v1)

A `ghcr.io/azzindani/pipeline:latest` image is generated by `pipeline_deploy.cicd_generate` once you wire your GitHub repo · not yet pushed publicly.

## Quick start

Three commands take you from empty directory to a green-tested project that any MCP-speaking agent can drive:

```bash
# 1. Scaffold a project (5 templates available)
pipeline init my-svc --type microservice-rust
cd my-svc

# 2. Run the inner loop (static + unit stages · seconds)
pipeline run fast

# 3. Start the MCP server · agents connect here
pipeline mcp
```

Profiles: `fast` (static + unit · agent inner loop) · `full` (+ container + integration) · `preflight` (+ security · clean Docker · pre-push gate) · `confirm` (CI parity check).

## Features

### 19 super tools · one stable surface

Every tool follows the same JSON envelope:

```jsonc
{ "action": "<verb>", "args": { /* action-specific */ } }
```

Returns:

```jsonc
{
  "ok": true,
  "data": { /* result */ },
  "next_suggested": ["pipeline_run.stage(fast)"],
  "memory_refs": ["session:abc-123"],
  "error": null
}
```

`next_suggested` closes the agent loop without prompting · `memory_refs` lets the agent hydrate prior context.

### What you get for free

- **Memory that learns** — every failure is logged with stage, error message, and (eventually) fix. `pipeline_memory.suggest_fix(error)` does keyword-matched retrieval. `known_issues` and `pattern_report` surface stage-level failure histograms.
- **Standards enforcement** — `pipeline_standards` clones [`azzindani/Standards`](https://github.com/azzindani/Standards), maps stack/project-type to the right subset, applies configs to your project, runs static gates as a compliance proxy.
- **Multi-repo workspace** — `pipeline_repo` registers external repos (any URL form: `https`, `ssh`, `git://`, `.git`, `owner/repo` shorthand, local path), digests them into structured summaries, extracts capabilities, ports across languages, compares two repos side-by-side.
- **Feasibility analysis** — paste URLs and a one-line idea into `pipeline_plan.link_ingest` + `feasibility`; Pipeline fetches each link, classifies it, builds a corpus, identifies the implied stack and core capabilities, returns a verdict (`yes` / `yes_with_caveats` / `needs_more_input`) with a plan skeleton and effort estimate.
- **Two MCP transports** — hand-rolled JSON-RPC 2.0 (default · stable) or official `rmcp` 1.6 SDK (set `PIPELINE_TRANSPORT=rmcp`).

## Pipeline workflow

The agent loop:

```
                ┌─────────────────────────────────────────┐
                │  pipeline_session.lock(project)         │
                │       ↓                                 │
                │  pipeline_session.handover()            │
                │       ↓                                 │
                │  agent reads PRD + last failure         │
                │       ↓                                 │
                │  agent generates code                   │
                │       ↓                                 │
   ┌────────────┤  pipeline_run.stage(fast)               │
   │            │  (static + unit · ~2-5 s)               │
   │            └──────────────┬──────────────────────────┘
   │   green                   │ red
   │                           ↓
   │            ┌─────────────────────────────────────────┐
   │            │  pipeline_run.fix_suggestion(stage)     │
   │            │       ↓                                 │
   │            │  pipeline_memory.suggest_fix(error)     │
   │            │       ↓                                 │
   │            │  agent applies fix → rerun fast         │
   │            └──────────────┬──────────────────────────┘
   │                           │
   ↓                           ↓
   pipeline_run.stage(full)    (loop continues)
       ↓
   pipeline_run.preflight()    ← clean Docker · static + unit + container + integration + security
       ↓
   pipeline_run.commit("message") + pipeline_run.push()
       ↓
   GitHub Actions confirm (parity check · static + unit only)
       ↓
   pipeline_deploy.target("staging") + .smoke + .health
       ↓
   pipeline_deploy.target("production") + .smoke + .health
```

Stage profiles:

| Profile | Stages | When | Target time |
|---|---|---|---|
| `fast` | static + unit | every change · agent inner loop | < 10s |
| `full` | + container + integration | pre-commit | < 2min |
| `preflight` | + security · clean Docker | pre-push gate | < 5min |
| `confirm` | static + unit only | GitHub Actions parity check | < 1min |

CI/CD lane separation: local owns `fast`/`full`/`preflight` · GitHub Actions runs `confirm` only · deploy promotion happens on tag push. The expensive Docker work has already passed locally before any CI runs.

## MCP integration

Pipeline serves the 19-tool surface over stdio JSON-RPC 2.0 (MCP `2024-11-05` protocol).

### Claude Code

Add to your `claude/settings.json` (or run `claude mcp add`):

```jsonc
{
  "mcpServers": {
    "pipeline": {
      "command": "pipeline",
      "args": ["mcp"]
    }
  }
}
```

For the rmcp-backed transport:

```jsonc
{
  "mcpServers": {
    "pipeline": {
      "command": "pipeline",
      "args": ["mcp"],
      "env": { "PIPELINE_TRANSPORT": "rmcp" }
    }
  }
}
```

### opencode / Codex / Kilo / other MCP clients

Same shape — any client that speaks MCP stdio works. Point the client's `command` field at the `pipeline` binary with `mcp` as the only argument.

### Local models (Ollama · LM Studio)

If your runner doesn't speak MCP natively, wrap Pipeline with an MCP-to-tool-calling shim. The 19-tool listing fits comfortably in a 16 K context window (the action lists are inlined in each tool description, so the agent picks an action without a second tool call).

### Verifying the connection

```bash
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"test","version":"0"}}}' | pipeline mcp
# Should print a JSON-RPC response with serverInfo: pipeline-mcp / 0.0.1
```

## Configuration

`pipeline.yaml` lives at the project root and tells Pipeline what stack it's looking at, which gates to enforce, and where to deploy. Generated by `pipeline init`; check it into git.

```yaml
project: my-svc
version: 0.0.1

stack:
  runtime: rust          # rust | python-uv | bun | node | go | typescript
  services:
    - postgres:16        # services compose up for the integration stage
    - redis:7

stages:
  fast:
    - static
    - unit
  full:
    - static
    - unit
    - container
    - integration
  preflight:
    - static
    - unit
    - container
    - integration
    - security

gates:
  coverage: 80           # fail if cargo-llvm-cov reports < 80% lines covered
  image_size_mb: 500     # fail if docker image > 500 MB
  critical_vulns: 0      # fail if Trivy reports any CRITICAL CVE

deploy:
  registry: ghcr.io/azzindani
  targets:
    staging:
      type: compose
      host: ssh://staging-server
    production:
      type: compose
      host: ssh://prod-server
      requires: manual_approval

maintenance:
  schedule: "0 9 * * 1"  # every Monday 9am
  auto_merge: true       # if pipeline green
  notify_on_fail: true
```

## Architecture

```
┌─────────────────────────────────────────────────────┐
│                  LOCAL (primary)                    │
│                                                     │
│  Coding Agent (Claude Code · Codex · Ollama · ...)  │
│       ↓ MCP protocol (stdio JSON-RPC)               │
│  Pipeline binary (Rust · single executable)        │
│  ├─ pipeline-mcp        (19 super tools)            │
│  ├─ pipeline-stages     (static · unit · container) │
│  ├─ pipeline-docker     (bollard / docker CLI)      │
│  ├─ pipeline-memory     (SQLite · sessions · runs)  │
│  ├─ pipeline-config     (pipeline.yaml schema)      │
│  ├─ pipeline-core       (Stage trait · profiles)    │
│  └─ pipeline-cli        (clap · binary entry)       │
│       ↓                                             │
│  Docker (ephemeral · clean container env)           │
│       ↓ all green                                   │
│  Git commit + push to GitHub                        │
└─────────────────────────────────────────────────────┘
           ↓ push triggers
┌─────────────────────────────────────────────────────┐
│              GITHUB ACTIONS (confirmation)          │
│  Stage 0 + Stage 1 only (fast · cheap)              │
│  Deploy trigger on main branch                      │
└─────────────────────────────────────────────────────┘
           ↓ green
┌─────────────────────────────────────────────────────┐
│                 DEPLOYMENT TARGET                   │
│  GHCR image registry                                │
│  SSH + compose / Kubernetes                         │
│  Health checks + auto-rollback                      │
└─────────────────────────────────────────────────────┘
```

### Hacking on a handler

Every super tool's handler lives at `crates/pipeline-mcp/src/handlers/<tool>.rs`. The pattern is uniform:

```rust
pub async fn handle(req: ToolRequest, state: Arc<ServerState>) -> ToolResponse {
    match req.action.as_str() {
        "my_action" => my_action(&req.args, state).await,
        // ...
        other => err(format!("unknown action 'pipeline_<tool>.{other}'")),
    }
}
```

Add an action by adding a match arm + a private `async fn`. Return `ToolResponse::ok(json!({...}))` on success or use the local `err(msg)` helper. The dispatcher in `crates/pipeline-mcp/src/dispatch.rs` is exhaustive over all 19 `ToolName` variants — no fallthrough.

## What makes Pipeline different

| Existing CI tools | Pipeline |
|---|---|
| CI is a push-time gate | CI is the agent's inner loop |
| Pipeline config is YAML | Pipeline is MCP-callable Rust |
| Local ≠ CI environment | Local IS CI via Docker |
| Agent and pipeline are separate | Agent drives pipeline natively |
| No project memory | Accumulates institutional knowledge in SQLite |
| Cloud-first | Local-first · cloud for confirmation |
| Works with one agent | Works with any agent via MCP |
| No standards enforcement | Enforces a [Standards repo](https://github.com/azzindani/Standards) across all projects |
| Cannot learn from other repos | Digests external repos · extracts capabilities · ports across languages |
| Cannot understand undocumented systems | Reverse engineers any target into structured digest |
| Knowledge lost between sessions | Knowledge exported · portable across agents and projects |

## Contributing

Pipeline runs itself. Before opening a PR:

```bash
pipeline run fast       # static + unit · must be green
pipeline run preflight  # full + security · for non-trivial changes
```

PR template, contributor guide, and code-of-conduct land at v1. For now: open an issue, describe the use case, propose a tool surface change if needed, ship a small commit. Standards repo (https://github.com/azzindani/Standards) is the source of truth for code quality decisions — defer to it when in doubt.
