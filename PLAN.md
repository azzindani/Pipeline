## 1. Vision recap (one paragraph)

Pipeline removes infrastructure burden from coding agents. Any agent — Claude Code · Codex · opencode · Kilo · Ollama · LM Studio · custom — locks into a project, gets full context handover, and drives the entire lifecycle (idea → PRD → scaffold → code → test → deploy → maintain) through a tight MCP surface. Local CI is the source of truth · GitHub Actions is confirmation · Docker is the substrate · standards are enforced automatically · memory accumulates per project. Faster validation loop → faster learning → faster shipping.

## 3. Super tool design

### 3.1 Why super tools (not 140 functions)

Listing 140 individual MCP tools to a model = listing tax + context rot. Local 7B–14B models lose coherence past ~30 tool descriptors · Claude Sonnet stays sharp longer but token cost still scales. Solution: **collapse by domain · dispatch by `action` parameter**. Trade verbose schemas for a small, memorable verb set.

| Surface shape | Tool count | Schema bytes (approx) | Local model accuracy |
|---|---|---|---|
| 140 flat functions | 140 | ~80 KB | Degrades past 30 tools |
| 19 super tools w/ action | 19 | ~25 KB | Stable across sizes |

### 3.3 Action dispatch pattern

Every super tool follows the same JSON shape:

```json
{
  "action": "<verb>",
  "args": { /* action-specific */ }
}
```

Returns:

```json
{
  "ok": true,
  "data": { /* action result */ },
  "next_suggested": ["pipeline_run.stage(fast)", "pipeline_test.run(unit)"],
  "memory_refs": ["err-1234", "session-abc"]
}
```

**`next_suggested`** is mandatory · closes the loop without prompting. **`memory_refs`** point to records the agent can hydrate via `pipeline_memory.recall`.

### 3.4 Schema strategy

Use JSONSchema `oneOf` keyed on `action` literal · each branch declares its own `args` schema. Generates clean per-action validation while keeping one tool descriptor.

```jsonc
{
  "name": "pipeline_docker",
  "description": "Docker · compose · image. Actions: build|run|exec|logs|inspect|rm|compose_up|compose_down|compose_ps|compose_logs|image_scan|image_promote|image_push|image_pull|dockerfile_generate|dockerfile_lint",
  "inputSchema": {
    "oneOf": [
      { "properties": { "action": { "const": "build" }, "args": { "required": ["target", "tag"] } } },
      { "properties": { "action": { "const": "compose_up" }, "args": { "required": ["services"] } } }
    ]
  }
}
```

Local models handle this well · Claude handles it trivially.

### 3.5 Anti-patterns to avoid

- ✗ Two tools that do the same thing under different names — agents pick wrong
- ✗ Free-form `command` strings — defeats the purpose of MCP
- ✗ Returning unstructured text — always JSON · text in a `summary` field
- ✗ Side-effects without confirmation tokens for destructive ops (deploy prod, drop schema, force push)

**`link_ingest(urls[])`** — accepts arbitrary URLs · classifies each as: blog · article · paper · video · docs · gist · package · social · github · gitlab · bitbucket · self-hosted-git · unknown. For text sources extracts content via headless browser (uses `pipeline_e2e.browser_launch` internals) · for PDFs extracts text · for videos pulls transcript · for git URLs delegates to `pipeline_repo.register`. Stores normalized notes in `.pipeline/research/` · embeds for semantic recall.

**`feasibility(sources)`** — `sources` shape: `{ text?, links[]?, repos[]?, capabilities[]? }`. Pipeline cross-references against: standards catalog · digested repos · memory of prior projects · current project capabilities. Returns:
```json
{
  "verdict": "yes" | "yes_with_caveats" | "needs_X" | "no",
  "identified_stack": ["postgres", "rust|go", "..."],
  "core_capabilities": ["auth", "rate-limit", "..."],
  "gaps": ["multi-tenant isolation strategy unclear"],
  "prior_art": [{ "repo_alias": "ref", "capability": "rate-limit" }],
  "plan_skeleton": { "features": [...], "milestones": [...] },
  "effort_estimate": { "poc": "2w", "mvp": "6w", "v1": "12w" },
  "risks": [{ "title": "...", "mitigation": "..." }],
  "next_suggested": ["pipeline_plan.create(type=...)"]
}
```
Output is structured · feeds directly into `plan.create` and `plan.prd_write` as seed data.

## 7. CI/CD lane separation

Three lanes · three jobs · never confused:

| Lane | Where | Stages | Trigger | Failure means |
|---|---|---|---|---|
| **Inner loop** | Local · agent-driven | fast (0+1) | every change | agent fixes immediately |
| **Pre-push gate** | Local · clean Docker | preflight (0+1+2+3+security) | `pipeline_run.preflight` | block push · agent fixes |
| **Confirmation** | GitHub Actions | confirm (0+1) | on push | parity check · should never fail if preflight passed |
| **Deploy promotion** | GitHub Actions | image build · scan · push to GHCR · deploy · smoke · health | tag or manual | auto-rollback |

Critical rule: ! GitHub Actions never duplicates Docker-heavy stages · those passed locally · CI = trust signal not gate.

## 8. Velocity metrics (must measure to prove acceleration)

Stored in `pipeline_runs` and `sessions` tables · surfaced via `pipeline_report.velocity_metrics`.

| Metric | Definition | Target by v1 |
|---|---|---|
| Inner loop time | Median seconds from agent change → green/red signal | < 10s |
| First-green latency | Time from `pipeline_session.start` → first all-green preflight | < 1 hr for typical feature |
| Fix-from-memory hit rate | % of failures where `pipeline_memory.suggest_fix` returned applicable fix | > 40% |
| Standards compliance score | % of standards passing on current branch | > 95% |
| Push-to-confirm parity | % of pushes where GitHub Actions matches local preflight result | > 99% |
| Deploy-to-rollback rate | % of deploys triggering auto-rollback | < 2% |
| Agent loop stability | Consecutive failures before agent gives up | track only · no target |

## 9. Multi-repo workflow

Registry at `.pipeline/repos/registry.json` · digests at `.pipeline/digests/<alias>.json`.

```
pipeline_repo.register(url, alias) — adds to workspace
pipeline_repo.digest(alias)        — extracts capabilities + structure
pipeline_repo.list_capabilities(alias)
pipeline_repo.compare(a, b, axis)  — side-by-side
pipeline_repo.extract(alias, capability, target_path)
                                   — agent-mediated · adapts to current project
pipeline_repo.port(alias, target_lang, scope)
pipeline_repo.re_analyze(alias, type)
                                   — RE on registered repo
```

License + secrets scan run on every digest. GPL/AGPL flagged → blocks extract unless user confirms.

## 11. Agent acceleration loop (the whole point)

Coding agents are fast at writing · slow at validating. Pipeline inverts this:

```
Agent: writes code
  ↓
pipeline_run.stage("fast")          ← 5–10s
  ↓
green? → next task
red? → pipeline_memory.suggest_fix(error) → agent applies → rerun
  ↓
batch done → pipeline_run.stage("full") ← Docker · clean
  ↓
green → pipeline_run.preflight → pipeline_run.commit + push
```

The faster this loop · the faster the agent learns what works. Memory makes the same failure cheaper every time it recurs. ! This loop is the product.
